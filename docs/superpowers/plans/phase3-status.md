## Safety attestation

Per user directive on 2026-04-24 and the `feedback_switch_write_safety.md` memory rule:

1. **No live-switch writes were performed by the agent during Phase 3 implementation.** Every write-path test mocks `procurve_client` operation functions and `app.write_safety.download_config`. Search for "live" in the test tree — all live tests remain opt-in under `backend/tests/live/*` and none were extended in Phase 3.
2. **Device password operations are NOT exposed in the HTTP API.** `procurve_client.operations.security.set_device_passwords` exists in the library for protocol parity, but no FastAPI route calls it. A dedicated negative test (`test_device_passwords_endpoint_does_not_exist_returns_404` in `backend/tests/app/test_api_security.py`) checks 7 plausible URL variants to lock this down.
3. **Every mutating endpoint routes through `app.write_safety.write_with_autobackup`**, which:
   - Returns 403 `{error: "read_only", ...}` when `READ_ONLY=true` (default).
   - Calls `download_config` and persists it via `BackupStore.save(..., trigger="pre-write")` *before* invoking the write.
   - Aborts the write if the backup cannot be saved.
4. **Lockout-risky writes require typed host confirmation** via `require_host_confirmation`. The frontend surfaces these through the shared `DangerConfirmDialog` component:
   - `PUT /configuration/ip` (management IP change)
   - `PUT /security/web-access` (HTTPS-only could orphan a non-TLS session)
   - `POST /security/web-managers` (authorized-manager list could lock out)
   - `POST /diagnostics/device-reset` (factory reset + reboot)
5. **Ping and link-test** are gated by `require_writable` but NOT auto-backed-up (they emit packets, they don't mutate config). Module docstring in `backend/app/api/diagnostics.py` documents this exception.
6. **Configuration report, support-tab, and all GET endpoints** are pure reads — no gates.

## Known follow-ups

These did not block Phase 3 closure but are worth tracking:

1. **User live-testing pending.** Per the Phase 3 user directive, the operator will exercise every write action against the live switch personally. A subsequent session should record the user's findings and patch any bugs that surface. Nothing in the code has been through a real CoS/DSCP/web-managers/etc. round-trip yet.
2. **QoS master-mode read.** The 2810-24G firmware does not expose a CGI to read the current CoS-vs-DSCP master mode. `QosSection` seeds local state to `IP_PRECEDENCE` (the canonical default); the UI is the source of truth until a `GET /qos/mode` endpoint materialises (would need new protocol analysis). Operator-induced drift from external tools will not be reflected.
3. **Port-config edit as modal, not inline.** `SetPortConfigRequest` has four editable fields; we chose a modal dialog over cramped inline editing. If operators prefer keyboard-first row editing, revisit in a UX polish pass.
4. **Bob-ports mixed-direction writes require two API calls.** `SetBobPortsRequest` is unidirectional (`enable: bool` + `ports: [...]`). When a user toggles both enables and disables simultaneously, the frontend fires two sequential `mutateAsync` calls. Each triggers a pre-write backup — two backups per "save". This is correct but chatty; could be worth a backend-side batch or a "batch pre-write" mode.
5. **Deferred Phase 2 follow-ups** still stand (real shadcn primitives, dark-mode palette, Playwright e2e, login redirect round-trip). Fresh in Phase 3 is the `DangerConfirmDialog` component — when shadcn is introduced, it should be refactored to use `shadcn/dialog` + `shadcn/button` + `shadcn/input` underneath while keeping the public API stable.
6. **VLAN + Stacking tabs NOT added.** The procurve_client library has ~14 VLAN ops and ~15 stacking ops that remain unwired. No placeholder tab was introduced in Phase 2 for these, so they remain a Phase 4+ candidate.
7. **Firmware / image uploads.** Explicitly excluded per the memory rule. Would require a separate user-approved design pass.
8. **Password change UI.** Out of scope permanently. The memory rule `feedback_switch_write_safety.md` treats this as ABSOLUTE BLOCKED — a password endpoint would require first updating the memory file and explicit, per-action user approval.
